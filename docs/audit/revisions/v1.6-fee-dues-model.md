# v1.6: the fee dues model (revises 07 §1 and F4/F17)

**Date:** 2026-10-30.

**Source:** the fee dues design, `docs/designs/fee-dues/fee-dues.md` (EGM Z6, Z8-1, D4).

**Class:** PRO. This is a technical model for the dues. It changes no Accounts policy.

The original wording in 07 is preserved. This file supersedes it where the two differ.

| Ref | v1.1 text | v1.6 text | Why |
|---|---|---|---|
| 07 §1 `fee_due` | registration, fee type, caption, due date, gross, concession, fine, currency, hold flag | The row holds registration, centre, plan, fee type, caption, due date, gross and currency, and is immutable. Concessions (F5), fines (D-FEE-6), holds and adjustments (F4) and allocations (F3) are separate append-only rows that reference `fee_due.id`. | An immutable due cannot carry amounts that change later. Each change is its own audited row. |
| 07 F4 enforcement | Row lock + check | Every writer of a registration's money first takes the advisory lock `fee-dues:<registrationId>`, then checks. | The app role holds no UPDATE privilege on dues, so `FOR UPDATE` cannot be used. The `fee_due` guard takes the same lock. |
| 07 F4/F17 formula | gross − concession + fine − Σ active allocations | Σ gross − Σ concessions + Σ fines ± Σ adjustments − Σ active allocations, computed from the rows | The amounts live in separate rows, not in columns on the due. |
| 07 §3 step 4 and "Concurrency" | Lock the student's open dues `FOR UPDATE`; row locks on dues | Take the `fee-dues:<registrationId>` advisory lock for each registration being paid. When there are several, take them in ascending id order. | The same reason as F4. Ascending order avoids deadlocks. |
