## Overview

A learner owes money only once dues exist for them. This piece copies a registration's dues from the published fee plan that prices its course at its centre in its year: one due per fee type and instalment, holding the amount, the due date and the currency.

Collection (F3) will allocate receipts against these dues, oldest first (D-FEE-4). Dues are never edited: concessions (F5) and corrections (F4) will add records of their own.

## Goals

*   **G1:** a holder of `fee.dues` at the registration's centre creates the dues of an ACTIVE registration, at an active centre, from its resolved published plan.
    *   A registration gets its dues once.
    *   Creation is refused when the registration has no plan, or when the plan's currency is not the centre's.
    *   The creation is audited [T-FD-001].
*   **G2:** each due equals its plan line, and the database proves it.
    *   The plan line must exist: a composite FK checks this.
    *   The amount and the due date must match the line and its instalment. The plan must be PUBLISHED. A guard checks both.
    *   A due is never updated or deleted, also not by SQL [T-FD-002].
*   **G3:** anyone with `student.view` at the centre sees the dues on the learner page, with a total per registration. Nobody else sees them [T-FD-001, smoke].
*   **G4:** the route checks the origin. An unknown or out-of-scope registration gives the same 404 as a missing one [T-FD-003].

## Non-Goals

*   Ad-hoc dues: they are created with their receipt (D-FEE-1, F3).
*   Concessions and schemes (F5); hold and amount change (F4); fines (D-FEE-6).
*   Balance carry-forward (R-063).
*   Bulk creation.
*   The legacy import (paused).
*   Creating dues inside `admit()`: admission must not depend on a fee plan existing (DD-2).

## Technical Plan

### Data model (migration `0026_fee_dues`)

The head is generated by `prisma migrate diff`; the rest is hand-written.

*   **`app.centre`** gains `currency char(3) not null default 'INR'`, with `centre_currency_check` `currency ~ '^[A-Z]{3}$'` (DD-4).
    *   There is no update grant, so the app cannot change it. A later piece lets `org.centre.manage` set it.
    *   `centre_write_guard` (0020) compares rows as `to_jsonb`, so a new column is covered there with no change.
*   **`app.registration`** gains `unique (id, centre_id)` (`registration_id_centre_id_key`), for the composite key below.
*   **`app.fee_due`:**

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | bigserial | no | primary key |
| `registration_id` | uuid | no | composite FK `(registration_id, centre_id)` → registration(id, centre_id), restrict |
| `centre_id` | int | no | part of the composite FK above |
| `academic_year` | text | no | |
| `plan_id` | int | no | composite FK `(plan_id, academic_year)` → fee_plan(id, academic_year), restrict |
| `fee_type_id` | int | no | composite FK `(plan_id, fee_type_id, caption_id)` → fee_plan_line(plan_id, fee_type_id, caption_id), restrict |
| `caption_id` | int | no | part of the composite FK above |
| `due_on` | date | no | |
| `gross` | numeric(14,2) | no | `fee_due_gross_check`: `gross >= 0` |
| `currency` | char(3) | no | `fee_due_currency_check` |
| `created_at` | timestamptz | no | default now(); stamped by the guard |
| `created_by` | uuid | no | FK → app_user; stamped by the guard |

*   Unique key `(registration_id, fee_type_id, caption_id)`.
*   The composite key into `fee_plan_line` needs `fee_plan_line_plan_id_fee_type_id_caption_id_key`, which exists (E-050).

**Guard `fee_due_guard`, BEFORE INSERT.** Invoker rights, rules only, nested ifs, and the constraint name in each message (as 0025):
1.  `created_at := now()` and `created_by := coalesce(app.session_user_id(), new.created_by)`.
2.  The plan is PUBLISHED: `select status … from app.fee_plan where id = new.plan_id`. Published plans never change, so no lock is needed. Otherwise it raises `fee_due_plan_guard`.
3.  The amount matches the line: `new.gross = (select amount from app.fee_plan_line where plan_id = new.plan_id and fee_type_id = new.fee_type_id and caption_id = new.caption_id)`.
4.  The due date matches the instalment: `new.due_on = (select due_on from app.fee_caption where id = new.caption_id)`. Instalments used by published plans are frozen, so this holds.
5.  The currency matches the plan: `new.currency = plan.currency`.
6.  The year matches the registration: it is the year of the registration's admission.

Checks 3–6 raise `fee_due_match_guard`.

**Immutability:** `fee_due_no_update_delete` (before update or delete) and `fee_due_no_truncate` (before truncate) both execute `app.ticket_immutable()`, as `call_log` does (0022). The test fixtures truncate under replica.

**RLS:** ENABLE and FORCE. The table has `centre_id`, so T-RLS-002 applies and needs four commands:
*   `select`: `centre_id = any ((select app.scoped_centre_ids('student.view'))::int[])`;
*   `insert`: `centre_id = any ((select app.scoped_centre_ids('fee.dues'))::int[])`;
*   `update` and `delete`: `using (false)`.

**Permission:** `('fee.dues', 'Create a learner''s fee dues from the fee plan', false)`, plus the `system_admin` grant.

**Grants:**
*   `select, insert (registration_id, centre_id, academic_year, plan_id, fee_type_id, caption_id, due_on, gross, currency) on app.fee_due`;
*   `usage` on its sequence.

### Server (`src/server/dues.ts`)

```ts
type DueRow = { id: string; feeTypeCode: string; feeTypeName: string; captionName: string; dueOn: string; gross: string; currency: string };
type RegistrationDues = { registrationId: string; courseCode: string; status: string; planId: number | null; dues: DueRow[];
  total: string; canCreate: boolean; reason: "has-dues" | "no-plan" | "currency" | "not-active" | "centre-inactive" | "no-permission" | null };
duesForPerson(session, personId): Promise<RegistrationDues[]>   // registrations the caller may view (student.view), oldest first
createDues(session, registrationId): Promise<{ count: number; total: string }>   // fee.dues.create
```

**`createDues`:**
1.  **Pre-flight.** The registration's id must be a UUID. Its centre is read in a `withScope` as `select centre_id from app.registration where id = $1`, under RLS. If no row comes back, the result is `RbacError("notfound")`, the same as for a missing registration (G4).
2.  **The action:** `scopedAction({ action: "fee.dues.create", permission: "fee.dues", centreId, targetType: "registration", targetId: registrationId })`. Inside the callback (it runs inside `duesDb`, see below):
    1.  `authorize(tx, "student.view", centreId)`: creating implies seeing (the batches pattern).
    2.  The trading gate: an inactive centre gives `centreId: centre is not active`.
    3.  `pg_advisory_xact_lock(hashtext('fee-dues:' || registrationId))`, so two clicks queue.
    4.  The registration is read with its course id, its year (via its admission) and its status. A status other than ACTIVE gives `registrationId: not active`.
    5.  The registration already has dues: `RbacError("duplicate", …, "fee.dues.exists")`.
    6.  `resolvePlan(tx, centreId, courseId, year)` returns null: `RbacError("invalid", …, "fee.dues.noplan")`.
    7.  The plan's currency is not `centre.currency`: `RbacError("invalid", …, "fee.dues.currency")`.
    8.  `insert into app.fee_due (...) select ... from app.fee_plan_line l join app.fee_caption c on c.id = l.caption_id where l.plan_id = $plan`. The count must be at least 1: a published plan always has lines.
    9.  The audit row is `{ after: { planId, version, count, total } }`, with the total from `sum(gross)::text`.
3.  **`duesDb`** maps 23505 to `fee.dues.exists` and the guard names to `fee.dues.mismatch`. A guard firing would mean a bug, so it is mapped rather than shown raw.

**`duesForPerson`:**
*   It reads `student.view`-visible registrations of the person: admission, then registration, then course.
*   For each registration it returns its dues as `gross::text` with the total as `sum(gross)::text`, and the plan that would apply.
*   It also returns `canCreate` and, when that is false, the `reason`:
    *   the caller lacks `fee.dues` at the registration's centre;
    *   the registration already has dues;
    *   the registration is not ACTIVE;
    *   the centre is not active;
    *   no plan applies;
    *   the plan's currency differs from the centre's.

**`ADMIN_MESSAGES`** gains:

| Key | Text |
|---|---|
| `fee.dues.exists` | "This course already has its dues." |
| `fee.dues.noplan` | "No published fee plan prices this course at this centre for that year." |
| `fee.dues.currency` | "The fee plan's currency differs from the centre's." |
| `fee.dues.mismatch` | "The dues did not match the fee plan; nothing was saved." |

### Page and route

*   **`/students/[personId]`** gains a "Fees" section for each registration. It is shown only to callers who see the learner, which the page already requires.
    *   It lists each due (fee type, instalment, due date, amount, shown through `inr()`) and the total.
    *   When `canCreate` is true, a "Create dues" form posts `registrationId`.
    *   Otherwise a line states the reason ("No fee plan for this course yet", and so on).
*   **`POST /students/[personId]/dues`** goes through `adminPost`. Its back and success target is `/students/<personId>` (with `?saved=1` on success). A malformed personId gives 404. Errors come back as `error` and `detail` on the learner page.
    *   `adminPost` gives no step-up: `scopedAction` does not ask for one, as in enquiries.

## Decisions

All six are recommended options.

1.  **DD-1:** One due per registration, fee type and instalment. Each is a copy of the resolved published plan, and dues are never repriced.
2.  **DD-2:** Dues are created explicitly by `fee.dues` at the centre, once per registration. Admission never depends on a plan.
3.  **DD-3:** A due is immutable. Concessions, holds, changes and allocations are separate records in later pieces.
4.  **DD-4:** Each centre has a currency, INR by default. Dues are refused when the plan's currency differs from the centre's.
5.  **DD-5:** Dues are visible with `student.view` at the centre.
6.  **DD-6:** Ad-hoc dues, carry-forward, schemes, fines, bulk creation and import are out of scope.

## Alternatives Considered

*   **Dues inside `admit()`.** Rejected: an admission would fail whenever head office had not yet published a plan. Dues would also need a fee permission that admitters may not hold.
*   **Computing dues from the plan on the fly, without a table.** Rejected: allocations (F3) need rows to point at, and a newer plan must not change what a learner owes.

## Risks and Limits

*   A registration admitted before its plan was published needs "Create dues" pressed later. The learner page says so (`no-plan`).
*   A registration that leaves ACTIVE keeps its dues. Cancelling or crediting them is F4.
