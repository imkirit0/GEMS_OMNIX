## Overview

The front office keeps a log of phone calls that are not (yet) enquiries (R-084, SRC). Calls about a known enquiry are already its follow-ups (E-042).

A separate table is needed for two reasons:
*   A follow-up needs an open enquiry (`0018:239`).
*   An enquiry needs a date of birth, a gender, a path and a course, which a caller often does not give.

This piece adds:
*   one append-only table, `app.call_log`;
*   `src/server/call-log.ts`;
*   the page `/calls` and its save route.

It reuses:
*   the enquiry permissions, `enquiryOptions()` and `canViewEnquiries()`;
*   `enquiry_may_receive` for the tele-caller;
*   `phoneDigits`, `ownText`, `isoDate`, `istToday`;
*   `app.ticket_immutable()` (0009), as 0018 uses it.

## Goals

*   **G1:** a holder of `enquiry.manage` at an active centre logs a call, with a field message for every rule. The database records who logged it and when. The audit row names the fields only [T-CL-001].
*   **G2:** a holder of `enquiry.view` lists the centre's calls with filters. Nobody else can, also by SQL. The log cannot be changed or deleted, also by SQL [T-CL-001, T-CL-002].
*   **G3:** the page and route check the origin and give field errors. A malformed or out-of-scope centre gives a 404 [T-CL-003, smoke].

## Non-Goals

*   R-080 front-office masters (DD-5, deferred: PRO to confirm).
*   Editing or deleting a call (DD-3).
*   Phone search (Z4, D8). It comes with a POST search form, as `/enquiries` has, when a screen needs it.
*   Showing who logged a call or the tele-caller's name. The R-084 table has neither (Z3, C2, D5). Both are stored for a later report.
*   Turning a call into an enquiry. The page links "New enquiry" with no pre-filled values, because personal data is not put in URLs.
*   Reports (Stage 7) and the legacy import (paused).

## Technical Plan (Architecture)

### Data model (migration `0022_call_log`)

The head of the migration is generated by `prisma migrate diff`. The Prisma model is `CallLog`, with `Centre.callLogs` and two `AppUser` back-relations (named relations).

```
app.call_log (
  id bigserial primary key,
  centre_id int not null references app.centre(id) on delete restrict on update restrict,
  phone text not null, name text, called_on date not null,
  call_type text not null, duration_min int, description text, note text, next_follow_up_on date,
  tele_caller uuid references app.app_user(id) on delete restrict on update restrict,
  by_user uuid not null references app.app_user(id) on delete restrict on update restrict,
  at timestamptz not null default now()
)
index (centre_id, called_on, id)
```

**Named checks.** The `ws`, `ctl` and `ctl_address` constants are copied from 0018's do-block into a 0022 do-block (Z9, C6, D7).

| Check | Rule |
|---|---|
| `call_log_phone_check` | `phone ~ '^[0-9]{10}$'` |
| `call_log_name_check` | No leading or trailing `ws`, no `ctl`, `char_length` 1–100 (as `enquiry_given_name_check`) |
| `call_log_call_type_check` | `in ('CALL_IN', 'CALL_OUT')`, the follow-up words (Z7) |
| `call_log_duration_min_check` | 0–600 (PMC) |
| `call_log_description_check`, `call_log_note_check` | No leading or trailing `ws`, no `ctl_address`, 1–1000 (as `enquiry_followup_note_check`) |
| `call_log_follow_up_check` | `next_follow_up_on >= called_on` |

**`call_log_guard`:**
*   BEFORE INSERT, `security invoker`, `set search_path = pg_catalog, app`. It is identical in shape to `enquiry_followup_guard`.
*   It sets `by_user := coalesce(app.session_user_id(), new.by_user)` and `at := now()`. Nothing else: the tele-caller is checked in the app, as `setCounsellor` does, with the foreign key as the database backstop (Z2, D3).
*   T-RLS-005 is unchanged, because the guard is not a definer.

**Immutability:**
*   `call_log_no_update_delete` (before update or delete) and `call_log_no_truncate` (before truncate) both execute `app.ticket_immutable()`.
*   The test fixtures truncate it under their `session_replication_role = replica` (C11, D6).
*   It is **not** in `scripts/etl/reset.sql`. It does not depend on admissions, so an ETL re-run must not delete real calls (D4).

**RLS.** The table has a `centre_id`, so T-RLS-002 requires four commands:
*   `select`: `centre_id = any ((select app.scoped_centre_ids('enquiry.view'))::int[])`.
*   `insert`: the same with `enquiry.manage`.
*   `update` and `delete`: `using (false)`, with no grant.
*   ENABLE and FORCE.

**Grants:**
*   `select, insert (id, centre_id, phone, name, called_on, call_type, duration_min, description, note, next_follow_up_on, tele_caller) on app.call_log`. The `id` is included because the id is reserved first (D1).
*   `usage on sequence app.call_log_id_seq`.

### Server (`src/server/call-log.ts`)

```ts
type CallInput = { centreId: number; phone: string; name?: string | null; calledOn?: string | null; callType: "CALL_IN" | "CALL_OUT";
  durationMin?: number | null; description?: string | null; note?: string | null; nextFollowUpOn?: string | null;
  teleCaller?: string | null };   // undefined = the default; null = none (C1)
type CallRow = { id: string; phone: string; name: string | null; calledOn: string; callType: "CALL_IN" | "CALL_OUT";
  durationMin: number | null; description: string | null; note: string | null; nextFollowUpOn: string | null; at: string };
type CallFilter = { from?: string; to?: string; callType?: string; dueBy?: string };

logCall(session, input: CallInput): Promise<{ id: string }>;                                   // call.create
listCalls(session, centreId, f?: CallFilter): Promise<{ rows: CallRow[]; truncated: boolean }>;
```

**`logCall`:**
1.  **Field rules,** before any database access, in the order of the table below.
2.  **Reserve the id:** `nextval('app.call_log_id_seq')::text` in a pre-flight `withScope`. The id becomes the audit target.
3.  **The action:** `scopedAction({ action: "call.create", permission: "enquiry.manage", centreId, targetType: "call", targetId: id })`. Inside its callback:
    1.  `authorize(tx, "enquiry.view", centreId)`, as `batches.ts` `writeGate` does. It is audited as DENIED, naming `enquiry.view`. Nothing enforces that manage implies view (`0005:157` allows manage alone), so this line makes `enquiry_may_receive`'s precondition certain (I1).
    2.  The trading gate (centre status only, as `createEnquiry`): `centreId: centre is not active`.
    3.  The tele-caller:
        *   **Default** (`undefined`): the logger, when `enquiry_may_receive(centre, session user)`; otherwise null.
        *   **Given:** it must pass `enquiry_may_receive`, else `teleCaller: inactive or unknown`.
        *   Step 1 guarantees the caller holds view, so the function's own view check passes (C9).
    4.  The insert, wrapped in `callDb`:
        *   23514 → `RbacError("invalid", "invalid value")`;
        *   23503 → `teleCaller: inactive or unknown` (the only foreign key that can fail: the centre is authorized first and `by_user` is set by the guard);
        *   42501 → `Forbidden`.
4.  **Audit:** `{ after: { fields: [<names of the non-null input fields, including the applied defaults>] } }`. No values: the enquiry DD-14 rule (Z1, D2, C13).

**`listCalls`:**
*   Runs in `withScope` with `authorize(tx, "enquiry.view", centreId)`. A refusal is `Forbidden`.
*   A non-integer centre gives `Forbidden` too, so the page answers 404 (D9).
*   **Filters (C4).** An invalid value matches nothing, as `listEnquiries` does:
    *   `from` and `to`: ISO dates, inclusive, on `called_on`;
    *   `callType`: `CALL_IN` or `CALL_OUT`;
    *   `dueBy`: `next_follow_up_on <= dueBy`.
*   **Order:** `called_on desc, id desc`. At most 200 rows (PMC); `truncated` is true when there are more.
*   **Formats:** `at` is ISO-8601 UTC (`to_json(at) #>> '{}'`, C5), and `calledOn` is `YYYY-MM-DD`.

**Centres for the page and the home link (Z6):** `enquiryOptions(session).centres`, which has `manage` and `active`, and `canViewEnquiries(session)`. There is no new function. A user may log at a centre when `manage && active` (C10).

**Field rules, in order:**

| Field | Rule | Messages |
|---|---|---|
| `centreId` | A safe integer ≥ 1 | `centreId: unknown` |
| `phone` | Required; `phoneDigits` | `phone: required`, `phone: 10 digits` |
| `name` | Optional; `ownText("name", v, 100)` | `name: invalid`, `name: invalid characters`, `name: 1-100 characters` |
| `calledOn` | Optional; the default is `istToday()`; `isoDate`; not after today | `calledOn: YYYY-MM-DD`, `calledOn: not a date`, `calledOn: not in the future` |
| `callType` | `CALL_IN` or `CALL_OUT` | `callType: one of the listed values` |
| `durationMin` | Optional; an integer 0–600 | `durationMin: 0-600` |
| `description`, `note` | Optional; `ownText(field, v, 1000, true)` | `<field>: invalid`, `<field>: invalid characters`, `<field>: 1-1000 characters` |
| `nextFollowUpOn` | Optional; `isoDate`; not before `calledOn` | `nextFollowUpOn: YYYY-MM-DD`, `nextFollowUpOn: not a date`, `nextFollowUpOn: not before calledOn` |
| `teleCaller` | `undefined`, `null`, or a UUID | `teleCaller: inactive or unknown` |

### Page and route

| Route | What |
|---|---|
| `/calls` | The centres of `enquiryOptions`. A 404 when there are none; one centre redirects to its list. |
| `/calls?centre=<id>[&from][&to][&type][&due]` | The list: date, phone, name, call type, duration, next follow-up, description.<br>The GET filters are dates and type only, so no personal data goes in the URL. `type` maps to `callType` and `due` to `dueBy`.<br>With `manage && active`, the page also shows the log form. Its tele-caller select lists `enquiryCounsellors(centre)`, preselects the logger when they are listed, and has a "None" option.<br>An inactive centre shows "This centre is not active." with the list and no form (C15).<br>A link to "New enquiry". |
| `POST /calls/save` | `adminPost`. The fields are the `CallInput` names. `""` becomes null first, then `durationMin` goes through `Number()` (C14). Back: `/calls?centre=<id>`. Success: `…&saved=1` ("Saved."). Errors use `adminPost`'s `error` and `detail=<field>`; typed values are not kept (C16). |

*   The page parses `centre` with `^\d{1,9}$` and checks it against the centre list. Anything else gives `notFound()` (D9).
*   The home page links Calls when `canViewEnquiries`. The enquiries page links Calls.

## Decisions

All five are recommended options under the standing instruction.

1.  **DD-1:** a general call log per centre with the fields above. The tele-caller is stored but not shown.
2.  **DD-2:** reuse `enquiry.view` and `enquiry.manage`. An inactive centre logs no calls.
3.  **DD-3:** append-only.
4.  **DD-4:** a list with date and type filters, newest first. A "New enquiry" link without pre-filled values. Phone search comes later, by POST.
5.  **DD-5:** the R-080 masters are deferred (PRO to confirm, D-GAP-2).

## Alternatives Considered

*   **Calls as enquiries, or as follow-ups.** Rejected for the reasons in the Overview.
*   **A new permission.** Rejected: the same people work enquiries.
*   **Editable entries.** Rejected: the log is an audit trail.
*   **A database tele-caller guard.** Rejected (Z2): the enquiry counsellor has none, and the app check plus the foreign key suffice.

## Risks and Limits

*   No phone search yet: a caller who rings back is found by date and type.
*   Tele-callers must hold `enquiry.manage` at the centre.
*   The list is capped at 200 rows; older calls are found by date range.
*   The driver-cause unwrap now appears in a third copy (`callDb`). It is a candidate for one shared helper later (Z11).
